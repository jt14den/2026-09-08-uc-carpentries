Concept 1

The one rule

A rectangular table processes the same way on every row:

  • every column is one variable
  • every row is one observation
  • each cell holds one value for that column

Some layouts are built to be read. A rectangular table is built to be processed. You can always build a nice view from the table; you cannot reliably process the pretty layout.

0:12–0:28. Name the two things they just did: worked in a copy, and started making a table that processes consistently. Think-pair-share on 2016_messy: what would a program choke on? Keep it to one value per column - don't add a sixth concept later.
Concept 2

Work in a copy

  • Treat the source file as read-only. You never edit the thing you were given.
  • Work in a named copy - 2016_clean, not Copy of Sheet1.
  • Duplicating a tab keeps both in the same file: a working copy, not a backup.
  • Version history helps, but the discipline is the point.
If you can't get back to the raw data, you have no data.
This is practice P2/C2. They already did it in the warm-up. Reinforce: the raw file is evidence. Renaming the copy on purpose is a habit worth nagging about.
Concept 1 · in practice

One value per cell

  • GQ & DF in one cell is two people
  • 45|0|0 in one cell is three counts
  • If you'd sum, filter, or group by it, it needs its own column

The demo: unmerge the title, split the packed PGR|PDRA|other column, recode the grey "cancelled" rows into a real cancelled column.

Concept 3

Formatting is not data

  • Merged titles, colour, spacing, row shading: not data
  • Grey-for-cancelled → a real cancelled column
  • None of it survives an export. Encode meaning as a value.
Colour-as-data is the classic trap. The cancelled rows in 2016_messy are only marked by grey shading plus one stray note. Ask: how would a script know these are cancelled? It wouldn't.
Practice 1

Missing values

  • Pick one representation per column and use it everywhere
  • Today: a blank cell for genuinely missing; 0 only for a measured zero
  • Never 0 for missing. Never -999.
  • Real work: decide what "missing" means here, write it down, then check how the next tool reads it
Ties into QC later: cancelled rows carry num_attended 0 in the dates tab. Is that a real zero or a missing value? It's a data-dictionary question, not an auto-blank.
Concept 4

A date has three states

All three can look identical in the cell.

ISNUMBER TRUE means it's a real date, not that the date is correct.

1:05–1:30. Format → Number to show stored value vs display. =ISNUMBER down the 2017_messy date column finds the text dates. =YEAR on the dates tab finds the 2017→2015 rows (events were in 2015), and the 1900s in 2016_messy.
Concept 4 · locale

Locale sets display, not the day

  • File → Settings → Locale sets the default date format and how Sheets reads ambiguous date text (03/04/2016 as Mar 4 or Apr 3)
  • Once Sheets has stored a real date, changing locale changes how it's written on screen - not which day it is
  • Don't use ISDATE(): ISDATE("July 20 1969") is TRUE, so text passes
  • Use =ISNUMBER() / =ISTEXT()
This replaces the lesson's 1900/1904 date-system material, which isn't a thing in Sheets. Set your sheet locale on purpose before class and say what it is.
Concept 4 · the defensive move

Make dates safe

  • Store dates as separate year / month / day columns, or as a recognised date shown yyyy-mm-dd
  • Set the locale on purpose and record it
  • Format with the full year before you export - a CSV keeps only what is shown
  • After any export, open the file and check the dates
"4 Mar" exports with no year; "2016-03-04" keeps it. The CSV writes the displayed string, so the fix happens before download, not after.
Concept 5

QA blocks · QC finds

1:30–1:55. QA is prevention, QC is detection - you need both. Sorting to find outliers: the two first moves are select the whole table and tick "Data has header row", or you shuffle rows apart from their keys.
Practice 2

Export to CSV

A CSV KEEPS

  • one table of plain text
  • the values, exactly as displayed

A CSV DROPS

  • formulas, formatting, tabs, validation
  • data types - everything is text
  • your change log
  • File → Download → CSV = current sheet only. Five tabs, five downloads.
  • GQ, DF gets wrapped as "GQ, DF" so the comma isn't a new column - but two values in one cell is still the real problem
  • Keep the working Sheet alongside the CSV, or export the change log as its own file

The Library of Congress lists CSV as a preferred format for datasets.

2:03–2:25. The date gotcha lands here again: format with the full year first. Comma quoting is automatic; don't dwell on it.
Practice 3

Write down what you changed

  • The CSV won't carry it. Version history is inside the Sheet, not the export.
  • A changelog tab, a README, or a dated note - anything the CSV can't drop
  • "Split trainer column 2026-09-08; 3 rows had two names" is enough
If someone asks "why is this number different?" - the answer is your change log.
Short. This is the habit that makes cleaning defensible six months later. Pair it with "keep the raw file".
Framing idea

Everything downstream reads your structure

AI does not fix messy data. It produces a fluent, plausible answer even when its assumptions are wrong. Fluent is not correct.

2:25–2:40. Data caution first: today's data is fictional. Do not paste real patron, student, personnel, health, licensed, or unpublished research data into an AI service unless it's approved.
Framing idea · verify

Check AI output by counting

Row count before and after. Compare values to the raw data you kept. Same check, every time.

Use a saved flawed output from a pre-class run, not a live model. After the id compare, ask: how would you catch this without the source_row_id column? (Row counts; compare to raw.) Optional live rerun to show output varies.

Recap

  • 1 columns are variables, rows observations, one value per cell
  • 2 the source file is read-only; work in a named copy
  • 3 formatting is not data
  • 4 a date is a value plus a display - or just text
  • 5 QA blocks bad input; QC finds bad values already there
  • represent missing values consistently, and decide what missing means
  • export to CSV for a portable single table; keep the docs alongside
  • write down what you changed
  • downstream tools - including AI - consume your structure; verify by counting
