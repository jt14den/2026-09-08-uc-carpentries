Why the shell

Why the command line?

  • So much runs on it - installing software, remote servers, containers, and HPC job scripts all assume shell basics
  • Your commands are the record - a pipeline you can re-run is a methods section a GUI never writes down
  • It's the glue between tools - an R script, a Python model, and someone's C binary all meet in the shell
  • AI coding agents work by typing shell commands - reviewing what an agent changed needs the same skill

Where it shows up

On an HPC cluster your job is a Bash script handed to a scheduler. Reproducibility tools - Snakemake, Nextflow, Docker, CI - are shell orchestrators. AI agents like Claude Code and Cursor run in a terminal you supervise.

On Zoom: in the chat - where have you hit a wall that a terminal would have gotten you past?

the shell is the layer HPC schedulers and AI agents both sit on top of

Concept 1 discuss

Why type when you can click?

  • A GUI is great for one file. It scales badly to hundreds.
  • A CLI lets you write instructions once and run them on 1, 100, or 10,000 files
  • The commands you type are a record - save them, re-run them, share them
  • It's the on-ramp to Python, R, Git, and working on a server

Navigating demo

Options change what a command does

  • ls -F - mark the type: / = directory, * = program, plain = file
  • ls -l - long form: size, date, name
  • ls -lh - human-readable sizes (5.3K, not 5369)
  • ls -a - show all, including hidden . names
  • Combine them: ls -Fa = ls -F -a
$ ls -F exercise-data/ north-pacific-gyre/ $ ls -l $ ls -lh $ ls -F -a ./ ../ exercise-data/ north-pacific-gyre/
an -F is an option (also flag / switch); a name to act on is an argument; short options use one -, long options use --

9:20-9:27 · ls options · DEMO · SWC Episode 2

SAY

  • Options modify the command. Capital vs lowercase matters: ls -s (show sizes) is not ls -S (sort by size).
  • Miss the space - ls-F - and the shell looks for a command called ls-F and fails.
  • -a reveals . (here) and .. (one level up) - we use both in a minute.

Navigating demo

How do I find the options?

  • ls --help - a summary printed to the screen (Linux, Git Bash)
  • man ls - the full manual (macOS, Linux). Space / b to page, / to search, q to quit
  • Only one of these may work on your system - that's normal
  • Or search the web for "ls unix man page"

a manual page (man page) is the reference doc shipped with the tool; an unknown option gives a clear error, not a crash

Files demo

Delete: rm (carefully)

  • rm quotes.txt - delete a file
  • No Trash. No "are you sure". No undo.
  • rm -i - prompt before each delete
  • rm won't touch a directory; rm -r deletes a directory and everything in it, no prompt
  • Safer: rm -r -i
$ rm quotes.txt $ ls quotes.txt ls: cannot access 'quotes.txt': No such file... $ rm thesis rm: cannot remove 'thesis': Is a directory $ rm -r thesis_backup
the shell unlinks the file - the disk space is reusable immediately, so recovery tools usually fail

SAY - say the danger twice.

  • There is no recycle bin. rm means gone.
  • rm -r on the wrong directory is the classic way people lose a project. ls first, then delete.
  • Some people alias rm to rm -i permanently.

Concept 3 · pipes & filters demo

Count with wc, save with >

  • wc file - lines, words, characters
  • wc -l / -w / -m - just lines / words / characters
  • wc -l *.pdb - every file, plus a total
  • > - send output to a file instead of the screen (overwrites silently)
  • cat file - print a file's contents (less for big ones)
$ wc cubane.pdb 20 156 1158 cubane.pdb $ wc -l *.pdb $ wc -l *.pdb > lengths.txt $ cat lengths.txt
redirecting to a file that a command is also reading corrupts it - never sort x > x

Pipes & filters demo

sort, head, tail, >>

  • sort - alphabetical; sort -n - numerical (10 after 9, not before)
  • head -n 1 file - first line; tail -n 1 file - last line
  • >> - append to a file instead of overwriting
  • None of these change the input file - they read it and write output
$ sort -n lengths.txt $ sort -n lengths.txt > sorted.txt $ head -n 1 sorted.txt 9 methane.pdb $ echo done >> sorted.txt
sort -n reads it as numbers, plain sort reads it as text - "2" vs "19" flips depending which

10:46-10:53 · sort/head/tail · DEMO · SWC Episode 4

SAY

  • Detour: sort ../numbers.txt vs sort -n ../numbers.txt - text sort puts "10" before "2".
  • sort -n prints to the screen; the file is unchanged. Redirect to keep it.
  • head -n 1 sorted.txt = the shortest file, because we sorted ascending.
  • > replaces, >> adds. Run an echo ... >> twice, cat to show it accumulating.

Pipes & filters demo

The pipe: |

  • | sends the output of the left command straight into the right one
  • No temp files. Chain as many stages as you like.
$ sort -n lengths.txt | head -n 1 $ wc -l *.pdb | sort -n $ wc -l *.pdb | sort -n | head -n 1
tools that read standard input and write standard output snap together - Unix calls this pipes and filters

10:53-11:00 · the pipe · DEMO · SWC Episode 4

SAY - build it up one stage at a time

  • We just used two temp files to answer "which file is shortest". The pipe removes them.
  • sort -n lengths.txt | head -n 1 - "sort's output goes straight into head".
  • wc -l *.pdb | sort -n - no temp files. Add | head -n 1 - the answer in one line.
  • Read it right to left: "head of sort of wc".

TYPE

sort -n lengths.txt | head -n 1
wc -l *.pdb | sort -n
wc -l *.pdb | sort -n | head -n 1

Concept 4 · automation

Loops: do it to the whole list

Three files - or three hundred. You don't type the command once per file.

for thing in list_of_things do operation_using $thing done
  • for repeats the block once per item in the list
  • each time round, the loop variable holds the current item; $thing reads its value
  • the prompt changes to > while the shell waits for the rest of the loop
this is a for loop; a variable walking a list is the same shape in every programming language you'll meet

11:16-11:22 · the loop idea · SWC Episode 5

SAY

  • Read the form aloud slowly: "for each thing in this list: do the following, using that thing."
  • The $ in front of the variable means "give me its value" - same $ idea as the prompt, different job.
  • Indentation is for humans; the shell doesn't need it.

Automation demo

A real loop

Automation demo

Check before you run

  • A loop does many things at once - or many mistakes at once
  • Put echo in front to preview the commands without running them
  • Looks right? Remove the echo and run it for real

a dry run - print what would happen before doing it - is a habit worth keeping for anything destructive

Concept 5 · scripts demo

Save commands as a script

  • A shell script is commands saved in a plain-text file
  • Run it with bash scriptname.sh - same result, one command, no retyping
  • A line starting with # is a comment - for the human, ignored by the shell
$ cd ../alkanes $ nano sorted.sh # in nano, type: # Sort files by their length. wc -l *.pdb | sort -n # ^O Enter, ^X $ bash sorted.sh
a script is a small program; saving your pipeline makes the work reproducible - run it again on new data, get the same steps

Scripts demo

Make the script take input

  • sorted.sh only ever sorts *.pdb in the current folder - not reusable
  • Inside a script, "$@" means "all the arguments the user typed"
  • Now the caller picks the files: bash sorted.sh *.pdb
  • "$1", "$2" - the first, second argument, if you want them one at a time
# sorted.sh # Sort files by their length. # Usage: bash sorted.sh file... wc -l "$@" | sort -n $ bash sorted.sh *.pdb $ bash sorted.sh ../creatures/*.dat
"$@" / "$1" are positional parameters; letting the caller choose the files is how every built-in command already works

You now have the words

What the field calls this

  • the $ the shell prints → the prompt
  • a -l after a command → an option / flag; a name to act on → an argument
  • the trail of names to a file → a path; from / is absolute, from here is relative
  • . and .. → current and parent directory
  • * and ? expanding to filenames → globbing
  • > / >> → redirection; | → a pipe
  • wc, sort, cut reading input, writing output → filters
  • where a command reads/writes by default → standard input / output
  • for … do … done → a for loop; $name → a variable
  • commands saved in a file → a script; "$@" → its arguments

You'll meet every one of these again in Git, Python, and on any server.
